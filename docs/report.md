# Отчёт о разработке сервиса DataScope

Документ фиксирует постановку задачи, принятые решения и результаты работы.
Технические детали — в [architecture.md](architecture.md), [api.md](api.md),
[data-model.md](data-model.md) и [metrics.md](metrics.md).

## 1. Цель и задачи

**Цель:** разработать сервис обработки и визуализации данных, который принимает
отчёты с техническими характеристиками видео и файлами трекинга, ведёт учёт
метрик по дням, месяцам и всему объёму и строит информативный график по каждой
метрике.

Задачи:

1. разобрать структуру исходного отчёта и выделить метрики двух листов;
2. спроектировать хранение, устойчивое к объёму данных;
3. реализовать загрузку, нормализацию и агрегацию;
4. построить дашборд с графиком на каждую метрику и KPI;
5. подготовить тесты, документацию и структуру репозитория для GitHub.

## 2. Исходные данные

`data/raw/data_detail-report.xlsx`, 35 эпизодов:

- лист **«Детали»** — 18 колонок: дата, сетап, сценарий, эпизод, камера/роль,
  устройство, файл, разрешение, кодек, битрейт, `r_frame_rate`, FPS, кадры,
  длительность, «плохие» интервалы и их доля, максимальный разрыв, категория;
- лист **«Трекеры»** — 15 колонок: дата, сетап, сценарий, эпизод, файл, точки,
  длительность, средняя частота и частота в начале/середине/конце, равномерность,
  пропуски, максимальный разрыв, категория;
- лист **«Сводка»** — счётчики категорий, которые сервис считает самостоятельно.

Особенности данных, повлиявшие на решения:

- над таблицей есть служебная строка `data | Детали`, шапка не в первой строке;
- числа с запятой (`6,55`), длительности в формате `1м 14с`;
- даты в формате `13.10.2026`, а имя файла содержит дату и время записи;
- встречаются битые файлы трекинга с нулевыми точками и частотой;
- отчётов может быть много, и они могут пересекаться по датам.

## 3. Требования

| № | Требование | Реализация |
|---|------------|------------|
| 1 | Большие объёмы | потоковый парсер, пакетная вставка, SQL-агрегации, индексы |
| 2 | Учёт по дням / месяцам / всему объёму | `granularity=day\|month\|all`, SQL-группировка и гистограммы |
| 3 | График по каждой метрике | 14 графиков на «Деталях», 12 на «Трекерах» |
| 4 | Структура проекта | слои `api / services / db / core / web`, docs, tests |
| 5 | Готовность к GitHub | README, лицензия, CI, changelog, `.gitignore`, скриншоты |

## 4. Проектирование

**Стек:** Python 3.10+, FastAPI, SQLite, Plotly (сервер), Plotly.js (клиент),
openpyxl, ванильный JS без сборки.

Почему так:

- **SQLite** — нулевая настройка, один файл, SQL-агрегации быстрее перебора
  DataFrame для повторяющихся запросов; при росте объёма заменяется на PostgreSQL
  без изменения API.
- **Plotly на сервере** — графики строятся один раз и кэшируются; клиент только
  отрисовывает JSON, поэтому логика визуализации тестируется питоновскими тестами.
- **Без сборки фронтенда** — проект запускается одной командой, что важно для
  демонстрации и проверки.

Слои:

```
HTTP (FastAPI) → сервисы (парсинг, агрегация, графики) → репозиторий (SQL) → SQLite
```

## 5. Ход реализации

1. **Анализ отчёта.** Составлен каталог метрик: типы, единицы, группы, алиасы
   заголовков, допустимые агрегации (`src/services/catalog.py`).
2. **Парсер.** Потоковое чтение `openpyxl`, автопоиск шапки, нормализация
   заголовков/чисел/дат/длительностей, восстановление FPS и частоты, сохранение
   неизвестных колонок, пропуск пустых строк.
3. **Хранение.** Три таблицы (`reports`, `details`, `trackers`), индексы,
   каскадное удаление, дедупликация по SHA-256, WAL.
4. **Агрегация.** Ряды по дням/месяцам, распределения, KPI; нулевые частоты
   исключаются из средних; категориальные — топ-8 + «Другие».
5. **Графики.** Три типа фигур: столбцы с усами и линией количества, гистограмма
   со средним, стек/рейтинг категорий; светлая и тёмная палитры.
6. **API.** 12 эндпоинтов, Pydantic-схемы, единый формат ошибок, кэш, GZip,
   OpenAPI.
7. **Интерфейс.** KPI, вкладки листов, фильтры, сетка графиков, таблица с поиском
   и сортировкой, загрузка drag-and-drop, экспорт, тёмная тема, ссылки на состояние.
8. **Тесты и документация.** 78 тестов, `ruff`, CI, 6 документов и скриншоты.

## 6. Результаты

- Сервис запускается командой `python -m src.main`, интерфейс — `http://127.0.0.1:8000`.
- Загружает исходный отчёт (35 эпизодов) и демонстрационный (215 эпизодов за
  36 съёмочных дней, вместе — 250) без ручной подготовки.
- Строит 26 интерактивных графиков и 8 KPI; переключает день/месяц/весь объём,
  агрегации, период и отчёт.
- Экспортирует выборку в CSV и XLSX; повторная загрузка файла не создаёт дубль.
- 78 тестов покрывают нормализацию, парсер, импорт, агрегации, API, экспорт
  и структуру графиков; линтер и тесты проходят локально и в CI.

Проверенные сценарии:

| Сценарий | Результат |
|----------|-----------|
| Первый запуск с пустой БД | импортированы 2 отчёта, 250 строк на каждом листе |
| Загрузка файла через API | 201, строки сохранены, кэш сброшен |
| Повторная загрузка того же файла | `duplicate: true`, дубля нет |
| Фильтр по периоду и отчёту | KPI и графики пересчитываются |
| Детализация «весь объём» | гистограммы и рейтинги категорий |
| Экспорт CSV/XLSX | файл открывается в Excel, кодировка корректна |
| Удаление отчёта | строки и файл удалены, дашборд пуст |
| Неверное расширение | 422 с понятным сообщением |

## 7. Ограничения

- импорт синхронный: для файлов в сотни тысяч строк нужна очередь задач;
- нет аутентификации — сервис для локального/доверенного контура;
- SQLite ограничивает параллельную запись (один писатель);
- таблица из 19 колонок требует горизонтальной прокрутки на узких экранах.

## 8. Выводы

Задача решена: сервис обрабатывает отчёты, ведёт учёт метрик в трёх разрезах и
даёт график на каждую колонку. Архитектура разделена по слоям, контракт API
описан и покрыт тестами, проект готов к публикации на GitHub и защите.
Дальнейшее развитие — очередь импорта, PostgreSQL, сравнение отчётов и экспорт
дашборда в PDF.
